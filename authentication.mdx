## Método de Autenticação

A API do Real Oficial utiliza **Bearer Token** para autenticação. Após fazer login, você receberá um token que deve ser enviado em todas as requisições subsequentes.

## Obtendo seu Token

<Steps>
  <Step title="Crie uma conta">
    Registre-se em [app.realoficial.com.br](https://app.realoficial.com.br).
  </Step>
  <Step title="Obtenha seu token">
    Use o endpoint `/login` para obter seu token ou acesse **Configurações > Segurança** no dashboard.
  </Step>
  <Step title="Use o token">
    Inclua o token no header `Authorization` de todas as requisições.
  </Step>
</Steps>

## Formato do Header

Todas as requisições autenticadas devem incluir o header `Authorization`:

```bash
Authorization: Bearer SEU_TOKEN_AQUI
```

## Header `Accept` (obrigatório)

<Warning>
Envie sempre `Accept: application/json`. Sem esse header, requisições que falham na
validação **não retornam JSON** — elas respondem com um **redirect `302`**, que é o
comportamento padrão do framework para clientes que não pedem JSON explicitamente.
</Warning>

```bash
Accept: application/json
```

O sintoma é enganoso porque nem todo erro se comporta igual: falhas de autenticação
(`401`) retornam JSON mesmo sem o header, enquanto erros de validação viram `302`. Um
SDK que esqueça o `Accept` funciona até a primeira requisição inválida e então recebe um
redirect sem corpo útil para parsear.

<CodeGroup>
```bash Sem o header (incorreto)
curl -X POST "https://api.realoficial.com.br/api/v1/createShorts" \
  -H "Authorization: Bearer seu_token_aqui" \
  -H "Content-Type: application/json" \
  -d '{ "url": "..." }'

# HTTP/2 302  — redirect, sem JSON
```

```bash Com o header (correto)
curl -X POST "https://api.realoficial.com.br/api/v1/createShorts" \
  -H "Authorization: Bearer seu_token_aqui" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{ "url": "..." }'

# HTTP/2 201 — ou 422 com os erros por campo
```
</CodeGroup>

<Note>
`Content-Type: application/json` descreve o **corpo que você envia** e é necessário em
requisições com body (`POST`, `PUT`). `Accept: application/json` descreve a **resposta que
você espera** e deve ser enviado em todas as requisições, inclusive `GET`.
</Note>

## Exemplo de Requisição

<CodeGroup>
```bash cURL
curl -X GET "https://api.realoficial.com.br/api/v1/user" \
  -H "Authorization: Bearer seu_token_aqui" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json"
```

```javascript JavaScript
const response = await fetch('https://api.realoficial.com.br/api/v1/user', {
  method: 'GET',
  headers: {
    'Authorization': 'Bearer seu_token_aqui',
    'Content-Type': 'application/json',
    'Accept': 'application/json'
  }
});

const data = await response.json();
```

```python Python
import requests

headers = {
    'Authorization': 'Bearer seu_token_aqui',
    'Content-Type': 'application/json',
    'Accept': 'application/json'
}

response = requests.get(
    'https://api.realoficial.com.br/api/v1/user',
    headers=headers
)

data = response.json()
```

```php PHP
$ch = curl_init();

curl_setopt_array($ch, [
    CURLOPT_URL => 'https://api.realoficial.com.br/api/v1/user',
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_HTTPHEADER => [
        'Authorization: Bearer seu_token_aqui',
        'Content-Type: application/json',
        'Accept: application/json'
    ]
]);

$response = curl_exec($ch);
$data = json_decode($response, true);
```
</CodeGroup>

## Tokens e Segurança

<Info>
  **Seu token é permanente.** Uma vez gerado, seu token não expira e permanece o mesmo. Guarde-o em um local seguro.
</Info>

<Warning>
  **Mantenha seu token seguro!** Nunca compartilhe ou exponha seu token em código público, repositórios Git ou logs.
</Warning>

## Códigos de Erro de Autenticação

| Código | Descrição |
|--------|-----------|
| `401` | Token inválido ou ausente |
| `403` | Token válido mas sem permissão para o recurso |

### Exemplo de resposta de erro

```json
{
  "error": "Token invalido ou expirado"
}
```
